## 3. 五个阶段

### 阶段 I：冷启动（11-04 07:32 – 11-04 24:00）

- 96 个 job 在 11-04 一次性建单，系统进入批量处理。
- 第一小时内完成第一次 `trial`、`validate`，09:03 写入第一条结果。
- 当天写入 10,616 条结果，占全期的 24.2%。
- 主 Agent 的早期消息后来被清理（见 §5），但子会话的派工提示保留下来。

### 阶段 II：批量爬坡（11-05 – 11-08）

- 11-05 达到全期消息峰值（19,586 条）和结果峰值（14,091 条）。
- 11-06 新建 21 个 job，结果 11,326 条；Watchdog 在 11-06 07:11 首次产生 `valution` 误名。
- 11-07 结果降至 2,007 条，11-08 仅 507 条；系统进入长尾修复，job 129 在 11-08 进入 deferred。
- 这一阶段是“行话”从任务词汇中长出来的主要窗口：派工/回报开始复用固定句式，`红位`、`对账`、`收口` 等词在 11-09 之后密集出现。

### 阶段 III：主会话回归与修复潮（11-09）

- 主会话保留消息从 11-09 01:29 开始；`subagent`、`valuation_recover`、`valuation_stop`、`valuation_supervise` 等工具首次出现在留存记录中。
- 新建 15 个 job，写入 1,926 条结果；第一次 `valuation_activate` 出现在 02:27。
- 主 Agent 开始对 108–129 等 `rule_error` 队列进行逐项收口，语言从“描述问题”转向“裁决/收口/单发”。

### 阶段 IV：词汇病理与高峰（11-10）

- 主 Agent 在 12:38 首次把 `valution` 当作 `subagent` 调用，此后当天共 2,277 次；全部报错。
- 当天工具错误 3,297 次，13:00 单小时 992 次；`valution` 一项占主 Agent 当天工具调用的绝大多数。
- 与此同时仍写入 2,942 条结果，说明“语言病理”没有立刻摧毁业务产出，但显著消耗了协调带宽。

### 阶段 V：收尾（11-11）

- 新建 5 个 job，写入 414 条结果；05:20:53 最后一条消息。
- 最终 154 个 job：149 active、4 failed、1 deferred；43,829 条结果：43,632 active、197 conflict。
- 系统在未完成全部修复的情况下停止；这不是“语言失败”，而是任务本身进入长尾与人工接口。

## 4. 主会话的历史缺口

- 主会话 `session_v2` 创建于 11-04 07:32，但 `session_message.seq` 从 28,766 开始，最早保留消息是 11-09 01:29。
- 主会话 `tokens_input=1,123,380,494`，保留消息逐条相加仅 `576,043,588`；约 48.7% 的输入 token 对应的事件已不可见。
- 推断为会话历史被清理/压缩（33 条 compaction），但原因无法从现有数据确定。
- 11-04 至 11-08 的主 Agent 语言，主要通过 756 条 parser 派工、676 条 reviewer 派工和 2,004 条 Watchdog 任务描述保留。论文的所有“早期主 Agent”结论都必须以这些派工文本为证据，不能声称直接观察了主会话。

## 5. 与论文叙事的关系

这条时间线支持三个判断：

1. **语言不是一次性设计出来的**：它在 11-04 的冷启动、11-05 的批量爬坡、11-08 的长尾、11-09 的修复潮、11-10 的病理高峰中逐步分层。
2. **语言与业务并行演化**：结果写入的高峰（11-05）早于行话的高峰（11-09/10），说明词汇不是业务成功的前提，而更像是在协调压力下长出的“二级基础设施”。
3. **病理与产出共存**：11-10 的 2,277 次 `valution` 与 2,942 条结果同时发生；不能用“结果多”反推“语言健康”，也不能用“语言病”反推“业务失败”。
